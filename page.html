Independent re-proof · arXiv 2609.18182v1 · Wiki Foundation Model (WFM)

The LLM Wiki idea holds up. The paper's numbers don't.

We re-ran every retrieval claim an outsider can check on the paper's own public test sets, with its stated embedding model: 3,000 questions, CPU only, no training and no API calls. Linking passages the way a wiki does really does beat flat chunks and knowledge-graph triples. The margins the paper reports rest on a baseline we measured points higher, and on eight cells that sit exactly a whole number below our measurement.

Lab 2 · Representation vs storage

Links buy most of the gain. Facts buy the rest at eight times the storage.

Same questions, same embedder, same corpus; only the stored representation changes. The graph variants use the LLM-extracted triples HippoRAG published for these corpora, searched with personalized PageRank at HippoRAG 2's default settings. Nothing is trained or tuned on the test questions.

Adding passages to a triple graph lifts average Recall@20 by points; the paper's own ablation reports 7.48. Plain title links, found by string matching with no LLM at all, reach at the storage of flat retrieval. The exception is MuSiQue, whose questions don't follow page links: there title links change Recall@20 by points, within noise, and the fact layer adds as much as the entity links do.

Lab 4 · Model context

How much context does the model have to read?

Recall@k counts passages. A model's context window counts tokens, and a fact costs about a tenth of a passage. So we read each method's ranked output in order and measured how many tokens pass before the gold answer first appears. Questions answered yes/no, or whose answer is already named in the question, are left out.

Facts are compact, but that doesn't help here: at almost every budget they carry the answer less often than passages do. The link-only methods keep the dense top five, so their gains start once the budget runs past those five passages (roughly 750 tokens) and peak around 2,048.

Lab 5 · Structure

What the link walk needs from the data

We traced every question's evidence through two overlays. Title links give each passage its own page title as a home and link it to the titles its text names, found by string match. NER links connect passages through the entities an LLM extracted from them. For links to help, three things have to hold: dense search lands on part of the evidence, the rest of the evidence is linked to that part, and the link is one hop from a dense hit.

Applications

Where the choice of representation pays off

Three places where these measurements change a design decision. The evidence line under each is measured here; the application itself is a proposal.

Documents with identifiers

A document wiki that needs no LLM to build

Technical documents already cite each other by identifier: a standard such as RFC 9110, a document number, a ticket such as TKT-4821. Link every chunk to the identifiers it names and to the document it belongs to, then walk those links from the top dense hits. That is the title-links method, with document numbers in place of page titles.

Agent context packing

Fill the context with linked passages, not facts

Facts look like the efficient way to spend a small context window: they are a tenth the length of a passage. They also carry the answer far less often. An agent packing evidence under a token budget should rank passages and follow their links, and keep a fact layer only to re-rank the first few slots, which is where it earns its storage.

Agent memory

Episodic memory as a linked wiki

Store each episode (a ticket, a run log, a hand-off note) as a passage, link it to the entities it mentions (systems, people, work items), and retrieve with the same walk from the top matches. Episodes that never share wording with the query but share an entity with a top hit come along.

Other corpora

The same structure, built from identifiers you already have

Nothing in the method is specific to Wikipedia. It needs six properties in the data, and business records usually carry them as identifiers.

  • Self-describing units. Each chunk embeds its home's name with its text.
  • One home per unit. Every chunk belongs to one identifiable thing: a page, a document number, a ticket.
  • Mentions of other identifiers. Chunks name other things by number or name. A match against the register of homes is a direct reference; a shared pattern such as a standard's number links chunks that cite the same thing. Structured fields such as parent or linked items count as mentions without any text extraction.
  • A dense foothold.
  • Evidence one hop away.
  • Specific identifiers. A link is worth the inverse of its identifier's degree. Hubs such as audit columns, lookup tables or a country everyone mentions connect everything and so say nothing.

Chunk records usually carry the vector, an access list, labels and a citation already. All three queries filter on the caller's access, so the step only passes through documents the caller can see: a hidden document can't be a seed, count toward a degree, or be returned.

-- generic SQL over a store with array fields and vector search; the service does the scoring
-- 1. seeds: the existing vector query, returning linkKeys
SELECT TOP 5 c.id, c.linkKeys, ... FROM c
WHERE ARRAY_CONTAINS(c.acl, @principal)
ORDER BY VECTOR_DISTANCE(c.embedding, @queryVector)

-- 2. degrees of the seeds' keys (or keep counts per key at ingest)
SELECT k AS key, COUNT(1) AS degree FROM c JOIN k IN c.linkKeys
WHERE ARRAY_CONTAINS(c.acl, @principal) AND ARRAY_CONTAINS(@seedKeys, k)
GROUP BY k

-- 3. units sharing a key, skipping keys above a degree cap
SELECT c.id, c.linkKeys, c.citation FROM c
WHERE ARRAY_CONTAINS(c.acl, @principal)
  AND EXISTS(SELECT VALUE k FROM k IN c.linkKeys WHERE ARRAY_CONTAINS(@keys, k))

Check a corpus before building its overlay. overlay.profile reports the structural potential of any corpus. With 30 to 50 labeled questions it also reports the dense foothold rate, how evidence pairs are linked, and how much missed evidence sits one hop from a seed: the measures that tracked the gain here. A corpus that profiles like MuSiQue under title links will not benefit from them.

Reproduce

Run it yourself

One script, pinned inputs. It downloads the benchmark files and cached OpenIE output from fixed HippoRAG commits and the paper source from arXiv v1, checks SHA-1 checksums, and refuses to run on anything that differs. Recall, storage, context coverage, the audit and this page are all regenerated from the run.

cd wfm-reproof
uv run reproof.py      # ~20 min cold on CPU, ~5 min with the embedding cache
# writes results/results.json, results/report.md, results/wfm-reproof.html

What this does not test

  • WFM itself. No code or weights were released, so its learned attention model, the attention-variance regularizer and the claim that it prevents attention collapse are unverified.
  • The 10.5× distributed-training speedup, which needs the authors' code and a multi-GPU cluster.
  • LLM-judged answer accuracy and the two long-term memory benchmarks (PersonaMem, RHELM).
  • HotpotQA in Lab 2 uses HippoRAG's older 9,221-passage corpus because that is the one its cached triples cover; Lab 1 uses the current 9,811-passage version.
  • HotpotQA and 2Wiki were built by following Wikipedia hyperlinks and Wikidata relations, which favors any link-based method. MuSiQue is the harder, less link-shaped test.
  • Answer-in-context is a proxy for answerability. It shows the answer string reached the model, not that the model used it.
